## 1. Введение

### 1.1 Назначение
Документ описывает требования к учебной системе attendance-students для учёта посещаемости студентов. Он предназначен для разработчика, преподавателей и пользователей системы.

### 1.2 Границы проекта
Система предназначена для хранения сведений о студентах и группах, регистрации посещаемости по занятиям, просмотра истории и формирования простых отчётов. В первую версию входят функции, необходимые для базового учёта посещаемости.

### 1.3 Термины
- **Посещаемость** — отметка о присутствии или отсутствии студента на занятии.
- **Пользователь** — преподаватель, студент или администратор системы.
- **Группа** — учебная группа студентов.
- **FR** — функциональное требование.
- **NFR** — нефункциональное требование.
- **MVP** — минимальная работоспособная версия продукта.

### 1.4 Ссылки
- Репозиторий проекта: https://github.com/elbarto1706011-bot/attendance-students
- ISO/IEC/IEEE 29148:2018 — инженерия требований.

## 2. Общее описание

### 2.1 Контекст продукта
attendance-students — учебный программный проект для ведения учёта посещаемости. Система заменяет ручное ведение списка отметок и позволяет хранить данные в структурированном виде.

### 2.2 Пользователи
- Преподаватель: выбирает группу и занятие, отмечает посещаемость, просматривает отчёты.
- Студент: просматривает собственную историю посещений.
- Администратор: управляет пользователями, студентами и группами.
- Руководство факультета: использует сводные отчёты.

### 2.3 Ограничения
- Доступ к функциям зависит от роли пользователя.
- Для работы необходимы устройство с браузером и доступ к системе.
- Точность отчётов зависит от корректности введённых отметок.
- Интеграции с внешними университетскими системами в текущую версию не входят.

### 2.4 Допущения и зависимости
Предполагается, что списки студентов и групп заранее внесены в систему. Пользователи имеют необходимые учётные записи. Требования описывают планируемое поведение системы; фактическое наличие каждой функции проверяется отдельно.

### 3.4 Требования к данным
Система должна хранить:
- сведения о пользователях и их ролях;
- сведения о студентах и принадлежности к учебным группам;
- сведения об учебных группах;
- сведения о занятиях (дата, группа);
- отметки посещаемости (студент, занятие, статус).

Для одной пары «студент — занятие» должна существовать не более чем одна актуальная отметка.

## 7. Валидация требований
Требования проверяются совместно с представителями пользователей. Для функциональных требований выполняются сценарные проверки: вход в систему, выбор группы, сохранение отметки, просмотр истории и формирование отчёта. Для нефункциональных требований проверяются время отклика, разграничение доступа, сохранность данных и корректность отображения текста.

## 8. Протокол интервью (учебная ролевая модель)
**Респондент:** преподаватель — основной пользователь системы.  
**Формат:** учебное интервью по сценарию лабораторной работы; ответы сформулированы как модель требований и не являются записью реального интервью.

1. **Вопрос:** Как сейчас отмечается посещаемость?  
   **Ответ:** Преподавателю нужен список студентов выбранной группы и возможность отметить присутствие или отсутствие.
2. **Вопрос:** Какие проблемы возникают при ручном учёте?  
   **Ответ:** Возможны ошибки при подсчёте пропусков и потеря записей.
3. **Вопрос:** Какие данные должны храниться?  
   **Ответ:** ФИО студента, группа, дата занятия и статус посещения.
4. **Вопрос:** Какие отчёты нужны?  
   **Ответ:** Просмотр посещаемости отдельного студента и сводный отчёт по группе за период.
5. **Вопрос:** Что важнее всего в первой версии?  
   **Ответ:** Вход в систему, список групп и студентов, отметка и сохранение посещаемости.
